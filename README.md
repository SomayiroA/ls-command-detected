# Event ID 117 - LS Command Detected in Requested URL



## Short Overview of the Investigation 🔬


This investigation examines a high-severity alert generated by LetsDefend's SOC167 detection rule. The rule detected the string ls in a requested URL, raising the possibility of command injection. Further investigation showed that the string appeared within the legitimate search term skills on the LetsDefend website.

*Investigation verdict*: False Positive - Legitimate web traffic.

## Investigation Steps 🕵️‍♂️


1. ### Alert Triage
Reviewed the alert metadata, source and destination IP addresses, hostname, HTTP method, and requested URL. The rule was triggered by the presence of ls, a Linux command commonly used to list files and directories.


2. ### URL and Traffic Analysis
Inspected the requested URL: https://letsdefend.io/blog/?s=skills

The string ls appeared inside the word skills, which was a search query rather than a command-injection payload.


3. ### Investigating Other Requests
I initially answered No when asked whether there was a different request or traffic pattern. This was incorrect.

I should have examined the other requests associated with the source and destination addresses to determine whether any showed suspicious behavior. Reviewing the surrounding traffic helped establish whether the alert represented an isolated keyword match or part of a broader attack pattern.

The documented investigation found the requests consistent with legitimate website browsing, with no evidence of command injection.


4. ### Final Classification
The alert was classified as a False Positive. The detection rule matched a substring within a legitimate search term, and the reviewed traffic did not indicate malicious activity.



## My Findings, Conclusions, and Response 🙋‍♀️


### Findings 


- The alert was triggered by the string ls in the requested URL.
- The URL contained the legitimate search term skills.
- The HTTP request used the standard GET method.
- Reviewing other traffic was necessary to validate the alert.
- No evidence of command injection or malicious execution was identified in the documented investigation.


### COnclusion


This was a False Positive caused by a keyword-based detection rule. The presence of ls alone was insufficient to establish malicious intent. 


### Response


1. I documented the evidence supporting the false-positive classification.
2. I then proceeded to close the alert according to the SOC playbook.
3. I recommend tuning the detection rule to identify actual command patterns instead of matching ls within ordinary words.
4. I'll keep on monitoring for genuine command-injection indicators and unusual requests.

## Lessons Learned ✍️


- A detection does not automatically mean an attack occurred: Rules can trigger on harmless text.
- *Check surrounding traffic*: When asked whether different requests exist, review related logs instead of making assumptions based on the initial URL.
- *Understand the context*: The string ls inside skills is different from an attempt to execute the Linux ls command.
- *Learn from mistakes*: I achieved a 50% playbook success rate and initially answered “No” to the different-traffic question. This reinforced the importance of reviewing related requests before reaching a conclusion.
